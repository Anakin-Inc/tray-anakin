# Tray.io — submission instructions

Real, self-serve, CLI-buildable — Tray connectors are built and deployed
with the `@trayio/cdk-cli` (`tray-cdk`) against a real Tray organization's
RBAC API token, no repo/PR process involved (unlike the Dagster/Fivetran/
Kubeflow submissions in this batch, which go through GitHub PRs to
third-party registries). Unlike Coda's public Pack gallery, there is no
public-marketplace submission step at all — deployment makes the connector
private to the deploying org, shared only by explicit permission grant. See
README.md's "Steps" section.

## Real CDK structure confirmed, not guessed

The task's starting assumption was that a Tray connector is defined by a
`connector.json`/`connector.ts` with `operations`, each having `input.schema`
(JSON Schema) and a `run` handler function. **That's not the real shape**,
and the difference matters enough to spell out:

- There is no single `connector.ts` — a CDK connector is a directory tree:
  root `connector.json` (metadata only — name/version/title/service/tags),
  plus one folder per operation under `src/`, each with its own
  `operation.json` (name/title/description), `input.ts`, `output.ts`,
  `handler.ts`, and `handler.test.ts`.
- **Input/output schemas are plain TypeScript types, not hand-written JSON
  Schema.** A field's UI metadata (title, description, default value,
  advanced-field grouping, static/dynamic dropdown options) comes from JSDoc
  tags on the type (`@title`, `@description`, `@default`, `@advanced`,
  `@items.title`, `@enumLabels`) — confirmed directly from
  `property-panel-ux/src/create_post/input.ts` in the real
  `trayio/CDK-examples-public` repo (cloned and read, not paraphrased from
  docs). JSON Schema *is* involved, but only as a **build output**: running
  `tray-cdk connector build` compiles each `input.ts`/`output.ts` into a
  sibling `input.json`/`output.json` (confirmed by actually running that
  command against this connector — see below). Those two files are
  machine-generated and gitignored, both here and in the real upstream repo
  (its root `.gitignore` has `**/src/**/input.json` /
  `**/src/**/output.json` verbatim) — not something a connector author
  writes by hand.
- There's no single `run` function shape. There are two: `usingHttp` (one
  request/response pair, configured via a fluent builder —
  `http.post(path).handleRequest(...).handleResponse(...)`) for single-call
  operations, and `usingComposite` (`async (ctx, input, invoke) => { ... }`,
  a real async function that can make as many calls as it wants, in any
  order, with any control flow) for multi-step operations. The real
  CDK-examples-public README states explicitly that composite is "most
  suited to... complex http operations that require multiple steps," which
  is exactly `url_scraper`/`agentic_search`'s shape here (submit, then poll
  in a loop) — not a workaround, the documented intended use.
- Auth isn't a bare API-key primitive either. The DSL has named auth-type
  wrappers (`TokenOperationHandlerAuth`, `Oauth1OperationHandlerAuth`,
  `Oauth2OperationHandlerAuth`, etc. — read directly from
  `node_modules/@trayio/cdk-dsl/dist/connector/operation/OperationHandler.d.ts`
  after a real `npm install`), and the connector's own `GlobalConfig.ts`
  only exposes `withBaseUrl`, `withBearerToken`, and `addHeader` (read
  directly from `OperationGlobalConfig.d.ts`) — there's no dedicated
  "API key" method, which is why (matching the real
  `connector-with-subdomain-example`'s handling of Shopify's
  `X-Shopify-Access-Token`) Anakin's `X-API-Key` header is wired via
  `addHeader`, and the auth type is `TokenOperationHandlerAuth` (the closest
  real fit for "one static user-supplied credential, no OAuth handshake").

## Extending to all 21 operations

The original build covered 3 of Anakin's 21 `api.anakin.io/v1` capabilities
(`url_scraper`, `search`, `agentic_search`) — the same subset built for
every other single-purpose Anakin integration in that batch. This pass adds
the remaining 18, bringing the connector to full parity with Anakin's own
MCP server's tool surface (`anakin-mcp/src/tools/*.ts`), which is the
ground truth this pass read from directly (`src/client.ts` for every
endpoint path/method/body shape, `src/tools/*.ts` for field names,
defaults, and behavior notes) — not guessed, and not re-derived from the
Tray connector's own prior operations.

- **Scaffolded with the real CLI, same as the original 3**: `tray-cdk
  connector add-operation <name> <http|composite>` was run once per new
  operation (18 real invocations, all `Success! Added operation: <name>`),
  then each `operation.json`/`input.ts`/`output.ts`/`handler.ts`/
  `handler.test.ts` was hand-edited from the scaffolded stub — not written
  from scratch and claimed to match the CLI's output.
- **http vs. composite, decided per operation from the real request shape**,
  same reasoning as the original 3's split (see "Not invented" below):
  8 new operations are genuinely async (submit-then-poll) → composite;
  10 are single-request → http; and 3 more (`wire_catalog`, `monitor_list`,
  `monitor_control`) are a *single* request but the path (and, for
  `monitor_control`, the HTTP method too) depends on the input — `usingHttp`
  takes one static path per operation with no conditional-segment support,
  so these were scaffolded as `http` first, found to need conditional
  logic, deleted, and re-scaffolded as `composite` (a single hand-built
  `axios` call, no polling) — the same "complex http operations... with
  conditional logic" case CDK-examples-public's README calls out as
  composite's other intended use, not just multi-step polling.
- **`wire_read_action`/`wire_write_action` are two operations, not one with
  a read/write flag** — deliberately mirroring anakin-mcp's own tool split
  in `src/tools/wire.ts`, whose comment there says the split is "mandatory"
  for that project's Connectors Directory listing (a single tool mixing
  safe/unsafe actions behind a flag isn't accepted there). That specific
  policy doesn't bind a private Tray connector, but the split is good
  practice on its own merits (an honest, separate description per
  operation) and was kept for that reason, not because the policy applies
  here.
- **The MCP server's client-side "no financial transactions" guard
  (`src/tools/policy.ts`) was deliberately NOT ported** to
  `wire_write_action` or `browser_task`. That guard exists specifically to
  satisfy Anthropic's Connectors Directory policy prohibiting a connector
  from "executing financial transactions or transferring assets" — its own
  comment says so directly, and says the guard is "defense-in-depth" on top
  of catalog-side enforcement, which is where the authoritative exclusion
  should live regardless of client. Since this Tray connector isn't being
  submitted to that directory, re-implementing an Anthropic-policy-specific
  regex guard here would be inventing unrequested behavior rather than
  modeling the real API; the operations pass `action_id`/`prompt` straight
  through, matching what `POST /wire/task` and `POST /ai/evaluate` actually
  accept.
- **`DynamicType` cast note**: three `usingHttp` handlers
  (`monitor_create`, `wire_login`, `wire_build`) build their request body as
  a plain `Record<string, unknown>` (for straightforward conditional field
  assignment) and pass it to `withBodyAsJson`, which is generically typed
  `<T extends DynamicType>` — `@trayio/commons`' `DynamicType` is a closed
  recursive union (`string | number | boolean | null | DynamicObject |
  DynamicArray`) that TypeScript won't structurally match against a
  `Record<string, unknown>`-typed value even when every actual value is a
  plain string/boolean/object, confirmed by a real `tsc` error before the
  fix (`Record<string, unknown>' is not assignable to parameter of type
  'DynamicType'`). Fixed with a narrow, explicitly-commented `as any` cast
  at the `withBodyAsJson` call site in each of the three handlers — the
  same kind of open-JSON-passthrough boundary already accepted elsewhere in
  this connector (`agentic_search`'s `schema` field, `wire_read_action`'s
  `params`), just hit here through the DSL's stricter `usingHttp` body
  typing rather than through a hand-typed `output.ts`.

## Not invented: the composite-vs-http decision

The task described `search` as synchronous and `url_scraper`/
`agentic_search` as submit-then-poll — that split is real (confirmed against
`anakin-py`'s `client.py`), and it maps directly onto the CDK's own
`usingHttp` (one call) vs. `usingComposite` (multi-step, dev-authored control
flow, real `axios` calls) distinction with no impedance mismatch: no
workaround, encoding trick, or unsupported feature was needed to model any
of the three operations, in contrast to this session's coda-anakin
submission, whose Coda formulas needed a JSON-encoded-string workaround for
`agentic-search`'s `schema` parameter and a hand-rolled polling deadline
because Coda formulas have no native long-running-job story at all.

## Not done

  Tray organization's RBAC API token (`TRAY_API_TOKEN`) and talks to Tray's

  was confirmed to be the actual, real gate (not guessed) by running the
  command and getting Tray's own "required env TRAY_API_TOKEN is not set"

- **Never tested against a real, valid Anakin API key**, for any of the 21
  operations. The 19 real 401s confirm request shape and routing, not
  response-body deserialization against a real success payload for the
  operations that need auth; `output.ts` in each operation folder was

  real 200s (`wire_discover`, `wire_catalog`) *do* confirm real response
  shapes, since those endpoints don't require auth at all — but that's 2 of
  21, not the norm.
- **Never opened the connector in the actual Tray builder UI** — so the
  rendered property-panel fields (titles, descriptions, default values coming
  from the JSDoc annotations in each `input.ts`) haven't been eyeballed,
  only reasoned about from `property-panel-ux`'s example and its screenshot
  in the real CDK-examples-public repo. This now spans 21 operations' worth
  of fields, not 3.
- Polling correctness under real job latency (does a real `url-scraper` job
  reliably finish inside the 100s budget? does `agentic-search` — described
  as "multi-stage" — sometimes need longer? does a real Wire action's
  `retry_after_ms` pacing behave as documented? does `browser_task` — known
  to sometimes need up to ~330s server-side, longer than this operation's
  100s poll budget — actually hit the `timeoutError` path in practice, and
  does re-running the step then correctly pick up the finished job?) is
  unverified for any of the 9 async operations — no live jobs were run
  end-to-end, same open question this session's coda-anakin submission
  flagged for its own 45s budget on a different platform.
- **The financial-transaction guard from anakin-mcp's `policy.ts` was
  deliberately not ported** to `wire_write_action`/`browser_task` (see
  "Extending to all 21 operations" above) — this is a documented design
  decision, not an oversight, but worth restating here: if this connector's
  deployment target ever needs directory-style compliance around executing
  payments/transfers via Wire or browser automation, that guard (or Wire's
  own catalog-side enforcement, which the MCP server's own comment says is
  the authoritative place for it) needs to be added or confirmed

- The `input.json`/`output.json` JSON Schema that `tray-cdk connector build`
  generates from each `input.ts`/`output.ts` was inspected once (to confirm

## Steps (needs the account owner)

See README.md's "Steps (needs the account owner)" section — RBAC token,
`TRAY_API_URL`/`TRAY_API_TOKEN`, `tray-cdk deployment create`, `tray-cdk
deployment get` to poll status, `tray-cdk permissions add` to share it with
other users in the org. No public-marketplace step exists for this
platform.
